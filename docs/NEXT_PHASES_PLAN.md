# Plan: measure, scale and deploy Logistics Automation

**Audience:** a coding agent working in this repository (`X:\projects\Logistics-Automation`).
**Starting point:** the Spring Boot rebuild on branch `feature/spring-boot-api` (Java 21 / Spring Boot API, Python Redis Streams worker, see `docs/SPRING_BOOT_REBUILD_PLAN.md` and `docs/SPRING_BOOT_REBUILD_NOTES.md`).
**Goal:** add three things, in this order:
- **Part A:** measured extraction accuracy (Gemini vs regex).
- **Part B:** observability, a load test and worker scaling, with measured numbers.
- **Part C:** S3 object storage and an AWS deployment.

Read this whole file before writing code. Do the parts in order (A, then B, then C). Every phase ends with **acceptance checks**: make them pass before moving on.

## 0. Ground rules (same as the rebuild, plus a few new ones)

1. **Branches.** If `feature/spring-boot-api` has been merged into `main`, branch from `main`; otherwise branch from `feature/spring-boot-api`. Use one branch per part: `feature/extraction-eval`, `feature/observability-load`, `feature/aws-deploy`. Commit per phase with clear messages. Never commit to `main`, never force-push.
2. **Never push `refs/backup/*`.** Push only the branch you are on (`git push origin <branch>`), never `--all` or `--mirror`.
3. **No secrets in git.** `.env` stays git-ignored. Never print, log or commit `GEMINI_API_KEY`, AWS keys, database passwords or tokens. New settings go in `.env.example` with empty values.
4. **No AI attribution** in commits, code or docs (no `Co-Authored-By:` trailers, no "generated by" notes).
5. **Every number must come from a run you actually did.** Each report states the date, the machine, the exact command, the dataset or load profile and the limitations. If a run was not done, write "not run" and why. Never estimate, round up or reuse numbers from elsewhere. This is the most important rule in this plan: these numbers will go on a resume and must survive an interviewer asking "how did you measure that?".
6. **Keep the API contract and the dashboard working.** Additions are fine; breaking changes are not.
7. **Spending money is the owner's decision.** You may not create cloud accounts, enter payment details, or run anything that creates billable cloud resources (`terraform apply`, `aws ... create-*`). Write the code and the commands; the owner runs them (Part C explains how).
8. If the plan does not fit the real code, stop and write the problem in `docs/NEXT_PHASES_NOTES.md` instead of guessing.

## Facts about the current code you need

- `backend/app/nlp.py`, `parse_invoice_text(text)`:
  - **Gemini path:** calls Gemini (`gemini-2.5-flash`, JSON schema `InvoiceFields`: `invoice_no`, `invoice_date`, `total_amount`, `gstin`, `hs_code`, `party`).
  - **Silent fallback:** on **any** error, or when no key is set, it silently falls back to `_fallback_regex_parse`.
  - **What the regex finds:** `invoice_no`, `total_amount` and `party`. It never finds `gstin`, `hs_code` or `invoice_date`.
- `backend/app/ocr.py`: EasyOCR, English, CPU. It returns `(text, details)` and only reads images.
- `backend/app/fraud.py`, Isolation Forest:
  - It is trained on **synthetic** data (`train_model.py`).
  - `party_txn_count` is hard-coded to 1 in the worker.
  - Do not make claims about its accuracy; it is out of scope here.
- `docker-compose.yml` sets `container_name:` on every service, including `worker`. A service with a fixed container name cannot be scaled with `--scale`.
- `backend/app/audit.py` reads the last line of `backend/models/ledger.txt` and appends a new hash-chained line **with no lock**. That is only safe with a single worker. `backend/models/ledger.txt` is a **tracked** file and uploads land in the bind-mounted `./sample_docs` folder, so load runs would pollute the repo.
- The API and the worker share files through the `./sample_docs:/data/uploads` volume. This is why they must run on the same host today; Part C removes that limit.

# Part A: extraction accuracy evaluation

Branch `feature/extraction-eval`. Needs a working `GEMINI_API_KEY` in `.env` (the owner provides it). If the key is missing or invalid, build everything, run the regex-only evaluation, and record the Gemini run as "not run".

### Phase A1: make the extraction path explicit

1. In `nlp.py`, split the logic into two public functions:
   - `parse_with_gemini(text) -> dict`, which **raises** on any error (no fallback inside);
   - `parse_with_regex(text) -> dict`.
2. Keep `parse_invoice_text(text)` with today's behaviour (try Gemini, fall back to regex), and also return which method was used: add `"extraction_method": "gemini" | "regex"` to the returned dict.
3. Log the reason for a fallback at WARNING (the exception class and a short message, never the key).
4. Add pytest unit tests:
   - The regex parser on a few fixed OCR strings.
   - `parse_invoice_text` falls back and sets `extraction_method="regex"` when `parse_with_gemini` is monkeypatched to raise.

**Acceptance:** existing worker tests and the new tests pass. No test calls the real Gemini API.

### Phase A2: build a labelled dataset

Create `eval/` at the repo root:

```
eval/
  generate_invoices.py   # synthetic invoice images + ground truth
  data/
    synthetic/           # generated PNGs + labels.jsonl (committed: small, no personal data)
    real/                # optional, owner-provided, labels.jsonl; git-ignored unless the owner says otherwise
  run_eval.py
  results/               # raw JSON results per run (committed)
```

1. `generate_invoices.py` (Pillow, fixed `--seed`) renders **60 invoice images** with known field values:
   - **Layouts:** 3 different ones (for example, header-table-footer, two-column, and a compact "tax invoice" format).
   - **Fonts:** 2 or more.
   - **Image noise to mimic scans:** mild rotation (±2°), blur, JPEG compression and noise on part of the set.
   - **Field values:**
     - Realistic invoice numbers.
     - Dates in 2–3 formats.
     - Totals with Indian thousands separators and `₹`, `Rs.` or `INR`.
     - Plausible party names.
     - GSTINs in the correct 15-character format.
     - HS codes taken from `backend/app/hsdata/hs_codes.csv`.
2. `labels.jsonl` has one line per image: `{"file": "...", "split": "dev"|"test", "invoice_no": ..., "invoice_date": "YYYY-MM-DD", "total_amount": 12345.0, "gstin": ..., "hs_code": ..., "party": ...}`.
3. **Split:**
   - Use 20 `dev` and 40 `test` images, fixed by seed.
   - **Hold one layout out for `test` only:** `dev` uses layouts 1-2, while `test` uses all 3 layouts, with layout 3 using different label wording (for example "Bill No." instead of "Invoice No.", "Amount Payable" instead of "Total").
   - **Freeze the generator before any parser runs:** commit `generate_invoices.py` and the data, then do not change them after the first `run_eval.py` run. If you must, regenerate, rerun everything and say so in the report.
   - Tuning (prompt or regex changes) may only look at `dev`. Report `test`.
   - **Fonts:** bundle open-licence fonts (for example DejaVu or Noto) in `eval/fonts/` with their licence files, so the generator does not depend on fonts installed on the machine.
   - **Dates:** dates are **day-first** (Indian format, e.g. `05/11/2026` = 5 November). Parse them day-first in scoring.
4. **Real invoices (optional):** if the owner adds any, they must be redacted (no real personal or company data) and labelled by hand. Report them as a separate table and never mix them into the synthetic numbers.

**Acceptance:** running `python eval/generate_invoices.py --seed 42` twice gives identical files and labels. The images open and look like invoices; spot-check 5 and describe them in the notes.

### Phase A3: evaluation runner

`eval/run_eval.py --split test --method gemini|regex [--limit N]`.

**Where it runs:** `app/ocr.py` loads EasyOCR at import time and the dependencies live in the worker image, so run the evaluation **inside the worker container** with `eval/` mounted. For example: `docker compose run --rm -v ./eval:/eval worker python /eval/run_eval.py ...`; put the exact command in the report. Keep the scoring code in its own module (`eval/scoring.py`) with **no import of `app.ocr` or `app.nlp`**, so its unit tests run in CI without EasyOCR.

Steps:

1. For each image: run `ocr.extract_text_from_image_bytes`, then the chosen parser. Record OCR time and parse time separately (`time.perf_counter`).
2. **Cache:** store OCR text and Gemini responses on disk, keyed by a SHA-256 of the image bytes (and of the OCR text for Gemini). Reruns then do not re-call Gemini; a `--no-cache` flag forces fresh calls. Put the cache directory in `.gitignore`.
3. **Rate limit:** throttle Gemini calls (default 1 request per 4 s, configurable) and retry 429s with backoff. Count every failed or fallback call; **never count a fallback result as a Gemini result.**
4. **Scoring, per field, after normalisation:**
   - Strings: trim, collapse whitespace, case-insensitive.
   - `total_amount`: numeric, equal within 0.01.
   - `invoice_date`: parse both sides to `YYYY-MM-DD`; unparseable counts as wrong.
   - `gstin`, `hs_code`, `invoice_no`: exact after normalisation.
   - `party`: exact after normalisation. Also report a "contains" match separately, and label it as lenient.
   - A field the method never extracts (for example `gstin` for regex) counts as wrong and is marked "not extracted by this method" in the report.
5. **Metrics, per method:**
   - per-field accuracy with a 95% Wilson interval;
   - document-level accuracy (all 6 fields right);
   - median and p95 OCR time and parse time;
   - number of Gemini errors and fallbacks.
6. Write raw results to `eval/results/<YYYY-MM-DD>_<method>_<split>.json` (per-document predictions and scores; no API key, no full Gemini response metadata).

**Acceptance:**
- `--method regex --split test` runs end to end.
- Unit tests for the scoring functions pass: amount tolerance, date normalisation, case and whitespace handling, and missing fields.

### Phase A4: report

`docs/eval/EXTRACTION_REPORT.md`:

- **Setup:**
  - The dataset: how it was generated, its size, the split, and the fact that it is synthetic.
  - The machine.
  - The exact commands.
  - Model name and temperature.
  - The date.
- **Results:**
  - A table of per-field accuracy (± 95% interval), Gemini vs regex, on `test`.
  - Document-level accuracy.
  - Timing (OCR and parse, median and p95).
  - Errors and fallbacks.
- **Error analysis:** 5–10 concrete failure examples with the cause: an OCR error, a parser error, or a label or format issue.
- **Limitations:**
  - The data is synthetic.
  - The layouts are limited.
  - The model was run once.
  - The real-invoice results, if any, come from a small separate set.
- If you changed the prompt or regex using `dev`, report the `test` results **before and after** the change.

**Acceptance:** every number in the report can be regenerated from a file in `eval/results/` with the command shown next to it.

# Part B: observability, load test, worker scaling

Branch `feature/observability-load` (from the Part A branch, or from `main` if Part A is merged).

### Phase B0: make the audit ledger safe for several workers

Before scaling workers, serialise audit appends:

1. In `audit.py`, take a Postgres transaction-level advisory lock (`SELECT pg_advisory_xact_lock(<fixed id>)`), read the previous hash from the **last `audit_logs` row** (`ORDER BY id DESC LIMIT 1`) instead of the file, insert the new row, then commit. Keep writing the ledger file line too, inside the same lock, so the file stays readable, but the database is the source of truth. Part C removes shared disks, so the file can become optional there.
2. Add `verify_chain()`: it recomputes every hash from the `audit_logs` rows in id order and reports the first broken link. Expose it as `python -m app.audit verify`.
3. Test: 3 threads (or processes) appending 50 entries each produce a chain that verifies.

**Acceptance:** the concurrency test passes, and `verify` passes on a fresh database after a few uploads.

### Phase B1: metrics

**Java API (`api-java`):**
1. Add `io.micrometer:micrometer-registry-prometheus`, expose `/actuator/prometheus` (also keep `/actuator/health`). HTTP server metrics (`http_server_requests_seconds`) come built in; enable histogram buckets for them (`management.metrics.distribution.percentiles-histogram.http.server.requests=true`).
2. Custom metrics:
   - `logistics_uploads_total{outcome="accepted|rejected|queue_failed"}` (counter);
   - `logistics_job_publish_seconds` (timer).

**Python worker:**
3. Add `prometheus_client`. Start an HTTP metrics server on port `9100` inside the container (no host port mapping). Metrics:
   - `logistics_jobs_total{outcome="success|retried|failed|skipped_duplicate"}` (counter);
   - `logistics_job_duration_seconds` (histogram, buckets suited to 0.1 s – 120 s);
   - `logistics_stage_duration_seconds{stage="ocr|parse|hs_lookup|score|db|audit"}` (histogram);
   - `logistics_queue_pending` and `logistics_queue_lag` (gauges, from `XINFO GROUPS logistics:jobs` and `XPENDING`; update every 5 s).

**Stack:**
4. `docker-compose.observability.yml` (an override file, used with `-f docker-compose.yml -f docker-compose.observability.yml`):
   - **Prometheus** (`prom/prometheus`, pinned version):
     - Scrapes `api:8000/actuator/prometheus`.
     - Scrapes the workers with `dns_sd_configs` (type A, name `worker`, port 9100), so every scaled replica is found.
     - Config in `observability/prometheus.yml`.
   - **Grafana** (`grafana/grafana`, pinned version):
     - A Prometheus data source and a dashboard, both provisioned from files in `observability/grafana/`.
     - The dashboard shows API request rate and p50/p95 latency, uploads by outcome, jobs by outcome, job and stage duration p50/p95, and queue pending and lag.
     - Login comes from `.env` (`GRAFANA_ADMIN_PASSWORD`); never hard-code it.
5. Remove `container_name:` from the `worker` service so it can be scaled. Check nothing else refers to `logistics_worker`.

**Acceptance:**
- With the override running, Prometheus shows the API and the worker targets as UP.
- After one upload, the dashboard shows non-zero panels.
- `docker compose up -d --scale worker=3` starts 3 workers, all 3 appear as Prometheus targets, and each has a different consumer name in `XINFO CONSUMERS`.

### Phase B2: stub mode for load testing

The real pipeline is dominated by EasyOCR on CPU (and Gemini rate limits), so system throughput must be measured with processing stubbed out:

1. Worker env `WORKER_STUB_MODE=true` (default **false**):
   - Skip OCR, Gemini and scoring.
   - Sleep `WORKER_STUB_DELAY_MS` (default 500).
   - Then write fixed fields, a transaction and the audit entry exactly like a real job.
   - Log a loud WARNING at start-up that stub mode is on.
   - Add `"extraction_method": "stub"` so stub results can never be mistaken for real ones.
2. A test that stub mode writes a transaction and is off by default.

### Phase B3: load tests

Use **k6** (`grafana/k6` Docker image, pinned version), scripts in `loadtests/`:

1. `upload_api.js`: `POST /upload` with a small fixed PNG at a constant arrival rate. Measures API latency only (the upload returns before processing).
2. `end_to_end.js`: the batch-drain scenario for L2. Upload N jobs, then poll each `/status/<uid>` every 250 ms until `completed`. Record the drain time (first upload to last completion) and the per-job end-to-end p50/p95. Fail if any job ends `failed`, or the whole drain exceeds 15 minutes.
3. `loadtests/README.md`: exact commands. Run k6 in Docker on the compose network, or against `localhost:8000`, and say which.

**Runs (all in stub mode unless stated):**

| ID | Scenario | Settings |
|---|---|---|
| L1 | API latency | `upload_api.js` at 5, 20 and 50 req/s, 60 s each, 1 worker |
| L2 | Worker scaling (batch drain) | upload **N = 300** jobs as fast as the API accepts them, then measure the time until all N are `completed`; completed jobs/s = N / drain time. Run with 1, 2 and 3 workers, 500 ms stub delay. After each run assert: transactions = N, no duplicate `document_id` in `transactions`, and `python -m app.audit verify` passes |
| L3 | Real pipeline sample (**required**) | real OCR, regex parsing (no Gemini), 20 sequential jobs, 1 worker: per-job time median/p95 and the stage breakdown from the metrics. Sleeping stub workers scale almost by construction, so this is the only real-pipeline number |

- Do each L1/L2 configuration **3 times**, report the **median** run, and keep all raw k6 JSON summaries in `loadtests/results/`.
- **Do not write load-test data into tracked paths.** For load runs, use a compose override that mounts uploads and the ledger on **named Docker volumes** (not `./sample_docs` or `backend/models`). Before committing, check `git status` shows no new files in `sample_docs/` or changes to `backend/models/ledger.txt`.
- Reset the database, stream and those volumes between runs (`docker compose down -v` removes named volumes, not bind mounts), and record how.

**Acceptance:** all L1, L2 and L3 runs complete, every L2 run passes its no-duplicate and ledger checks, and the raw results are committed.

### Phase B4: report

`docs/perf/LOAD_TEST_REPORT.md`:

- **Setup:**
  - Machine: CPU, cores, RAM and OS.
  - The fact that the load generator and the system ran on the same machine.
  - Docker resource limits.
  - Stub delay.
  - Dates.
- **Results:**
  - **L1:** achieved request rate, error rate and API p50/p95/p99 at each load.
  - **L2:** completed jobs/s and end-to-end p50/p95 for 1, 2 and 3 workers, and the speed-up relative to 1 worker.
  - **L3:** per-job real-pipeline time, if run.
  - Two Grafana screenshots, committed under `docs/perf/img/`.
- **Limitations:**
  - It is a single machine.
  - It uses stub processing.
  - Scaling is capped by local CPU.
  - These are not production numbers.

**Acceptance:** every number in the report maps to a raw file in `loadtests/results/`.

# Part C: S3 storage and AWS deployment

Branch `feature/aws-deploy`. Parts C1–C2 run locally and cost nothing. C3–C4 create AWS resources: write everything, but **the owner runs the commands that create or change cloud resources.**

### Phase C1: object storage abstraction (local, MinIO)

1. **Java:**
   - A `StorageService` interface with two implementations:
     - `LocalFileStorageService` (today's behaviour);
     - `S3StorageService` (AWS SDK for Java v2, `software.amazon.awssdk:s3`).
   - Chosen by `app.storage.type=local|s3`.
   - S3 settings: bucket, region, an optional endpoint override and path-style access (for MinIO).
   - Object key: `uploads/<uid>`.
2. **Job message:** add a field `storage_uri`, which is `s3://<bucket>/uploads/<uid>` or `file:///data/uploads/<uid>`. Keep `file_path` for the local type, for compatibility.
3. **Worker:** read the file through a small `storage.py`, using `boto3` for `s3://` and plain file reads for `file://`. Same settings, read from env.
4. **Compose:**
   - Add a local S3-compatible service and a one-shot init container that creates the bucket. **Check what is actually published before pinning:** MinIO changed how it distributes its free community edition in late 2025 and may no longer publish current Docker images. Confirm the image and tag can be pulled today; if not, use another S3-compatible server (for example LocalStack or SeaweedFS's S3 gateway). Record the choice and the reason in the notes file. The rest of this plan says "MinIO" for short.
   - Credentials come from `.env` (for example `S3_LOCAL_ACCESS_KEY` / `S3_LOCAL_SECRET_KEY`, empty in `.env.example`).
   - Default local mode becomes `s3` against MinIO.
   - Remove the shared uploads volume from `api` and `worker` once S3 mode works.
5. **Tests:**
   - Java: a Testcontainers container for the same local S3 server (for example `MinIOContainer` or `LocalStackContainer`). The test checks that an upload stores the object and the job carries the right `storage_uri`.
   - Python: `moto` (`mock_aws`), worker reads the object.

**Acceptance:**
- The full stack works with no shared volume between `api` and `worker`.
- `--scale worker=3` still works.
- All tests pass.

### Phase C2: images and CI

1. Production-ready images:
   - `api-java` already has a multi-stage image.
   - `backend` (the worker) should not run with `--reload` or as root.
   - The frontend gets a production image: a multi-stage `npm run build`, served by `nginx:alpine`. `VITE_API_URL` is a build argument.
2. **CI:** on push to `main`, build all three images and push them to **Amazon ECR**.
   - Authenticate with **GitHub OIDC** (`aws-actions/configure-aws-credentials` with `role-to-assume`). **No long-lived AWS keys in GitHub secrets.**
   - Keep this job disabled (`if: false` or a manual `workflow_dispatch`) until the owner has created the role in C3.

**Acceptance:** all three images build locally, and the frontend image serves the dashboard on port 80.

### Phase C3: infrastructure as code (Terraform), owner applies

Write Terraform in `infra/terraform/` (pinned AWS provider; remote state optional, document the choice). Region `ap-south-1` (Mumbai) unless the owner says otherwise. Resources:

- **S3 bucket** for uploads:
  - Block all public access.
  - Server-side encryption (SSE-S3).
  - A lifecycle rule that expires objects after 30 days.
- **ECR repositories:** `logistics-api`, `logistics-worker` and `logistics-frontend`, with a lifecycle policy that keeps the last 10 images.
- **IAM:**
  - An EC2 instance role with **least privilege**: `s3:GetObject`/`PutObject` on this bucket only, ECR pull, SSM managed core.
  - A GitHub OIDC provider and deploy role, limited to this repo's `main` branch, with ECR push and SSM `SendCommand` on the instance only.
- **Networking:** the default VPC is fine. A security group allows inbound 80/443 from anywhere and **no SSH port** (use SSM Session Manager for shell access).
- **Compute:** one EC2 instance running Docker Compose (Amazon Linux 2023, with user data that installs Docker and the compose plugin).
  - EasyOCR + PyTorch need RAM, so 1 GB instances will struggle.
  - Make the instance type a variable, and document the trade-off and current price in the README. The owner picks.
- **Database:** a variable `use_rds`.
  - `true`: RDS Postgres (smallest class, 20 GB, not publicly accessible, security group only from the instance).
  - `false`: Postgres in a container on the instance with a named volume.
  - Document the cost difference.
- **Redis:** in a container on the instance. ElastiCache is overkill and costly here.
- **Secrets:**
  - The DB password, Gemini key and Grafana password live in **SSM Parameter Store** (SecureString). The instance reads them at start-up into the compose environment.
  - Generate the DB password with `random_password` and write it to SSM. Note that **Terraform state then contains it in plain text**, so state stays **local on the owner's machine** (or in a private, encrypted S3 backend if the owner sets one up later). Add `*.tfstate`, `*.tfstate.*`, `.terraform/`, `*.tfvars` and `crash.log` to `.gitignore` **before** the first `terraform init`.
  - **The Gemini key never goes into Terraform.** The owner puts it into SSM by CLI (`aws ssm put-parameter --name /logistics/gemini_api_key --type SecureString --value ...`), and Terraform only grants the instance role read access to that parameter name.
- **Outputs:** the instance's public DNS, the bucket name, the ECR URLs and the deploy role ARN.

Add `infra/README.md` with the exact owner steps:

1. Create or confirm an AWS account. Set up an **AWS Budget with an email alert (for example 5–10 USD) first**. Check the current free-tier and credit terms on the AWS website, because they change.
2. Configure local credentials (`aws configure sso` or an IAM user for Terraform only).
3. `terraform init && terraform plan`. Read the plan, then `terraform apply`.
4. Put the role ARN in the GitHub repo variables, then enable the CI deploy job.
5. **Teardown:** `terraform destroy`, to stop all charges. Also say which resources keep costing money while they exist (EC2 running hours, RDS, EBS, public IPv4 address).

**Acceptance:** `terraform fmt -check` and `terraform validate` pass. The agent must not run `apply`.

### Phase C4: deploy and verify (owner runs, agent writes the scripts)

**Before anything is public, lock it down:**
- Require an API key header on `/upload`, `/status/**` and `/transaction/**` (Spring Security filter, key from SSM). Add a rate limit on `/upload` (for example 10 per minute per IP, in nginx or the API). Otherwise anyone on the internet could upload files and use up the Gemini quota.
- nginx must **not** proxy `/actuator/**` (block it, except `/actuator/health` if needed).
- Prometheus and Grafana do **not** run on the public host, or listen only on localhost and are reached with an SSM port-forward.
- Alternative for a short demo: restrict the security group's port 80/443 to the owner's IP only. Document which option was used.

1. **Deployment:** add `deploy/docker-compose.prod.yml`. The CI job builds and pushes images, then uses `aws ssm send-command` to make the instance `docker compose pull && docker compose up -d`. The prod file differs from local:
   - images come from ECR;
   - S3 is real (no MinIO);
   - the database is RDS or a container, depending on `use_rds`;
   - the frontend is served on port 80;
   - the API sits behind the same host.
   Either put an nginx reverse proxy in front with `/api` → api:8000 and build the frontend with `VITE_API_URL=/api`, or set it to the public URL. Document the choice.
2. **Optional:** HTTPS with a domain (Caddy or certbot). Skip it if there is no domain.
3. **Smoke test** script `deploy/smoke_test.sh <base-url>`:
   - `/health` returns ok;
   - upload `sample_docs/invoice1.jpg`;
   - poll `/status` until `completed` or 180 s;
   - confirm the object exists in S3 (`aws s3 ls`).
4. **Optional:** rerun L1/L2 from Part B against the AWS deployment from your laptop, and add them to the load-test report as a **separate** table (network latency included, say so).

**Acceptance (filled in by the owner or agent after the owner applies):**
- The smoke test passes against the public URL.
- The uploaded file is in S3.
- No AWS keys are on the instance (the instance role is used).
- The budget alert exists.
- Record the instance type, whether RDS was used, and the date in `docs/DEPLOY.md`.
